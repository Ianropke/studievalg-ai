# Methodological Documentation & Analytics Specifications
**Studievalg-AI — Analytical Framework & Model Architecture (v2026.6 O*NET 31.0 partial migration)**

---

## 1. System Overview

Studievalg-AI is a deterministic, data-first decision-support system. Numerical recommendation components are calculated by explicit code and supplied datasets; an LLM is not the source of numerical truth.

The system distinguishes these epistemic layers:

1. **OBSERVED** — directly measured values from a named source dataset for a documented population and period.
2. **DERIVED** — deterministic transformations of documented observations.
3. **CROSSWALK** — values transferred through a documented taxonomy/classification mapping.
4. **MODEL** — estimates produced from explicit assumptions or formulas.
5. **PROVENANCE_REQUIRED / UNKNOWN** — insufficient programme-level evidence for an empirical claim.

A source registry is not itself evidence for a programme. A programme-level claim is evidence-backed only when a concrete source-to-claim relationship has been established.

---

## 2. Canonical Data Architecture & Provenance

```text
Source dataset
    ↓
Ingestion + integrity validation
    ↓
Canonical programme / occupation mapping
    ↓
Metric transformation / model calculation
    ↓
Recommendation scoring
    ↓
Programme-specific evidence and provenance
    ↓
UI explanation
```

Every important programme-level metric should eventually carry:

- source organisation
- dataset/table
- observation period
- raw metric
- transformation
- mapping method
- coverage
- epistemic status
- confidence

Missing provenance must be reported as `UNKNOWN` or `PROVENANCE_REQUIRED`; it must never be upgraded merely because a source appears in the global evidence registry.

The machine-readable audit is generated by `etl/build_data_provenance_report.py` and written to `data/DATA_PROVENANCE_REPORT.json`.

## 3. Metric Definitions

| Metric | Status | Definition |
|---|---|---|
| `automation_risk` | Model / crosswalk | Estimated occupational task exposure to direct AI substitution. Not a Danish observed job-loss rate or automation probability. |
| `augmentation_potential` | Model / crosswalk | Estimated potential for AI to augment human work. |
| `ai_resilience` | Derived model index | `clamp(0.75 * (1 - automation_risk) + 0.25 * augmentation_potential, 0.1, 1.0)`. This is a model indicator, not a forecast. |
| `labour_demand` | Derived only when programme provenance is established | May be derived from observed employment/unemployment data in the strict analytics pipeline; the static client catalogue remains `PROVENANCE_REQUIRED` until its programme mapping/source is carried with the value. |
| `salary_growth` | Derived only when programme provenance is established | May be derived from documented salary series in the strict analytics pipeline; the static client catalogue remains `PROVENANCE_REQUIRED` until its programme mapping/source is carried with the value. |

`automation_exposure` is not a separate empirical metric and must not be displayed as an independently measured variable.

The canonical AI-resilience score gives 75% weight to inverse automation risk and 25% weight to augmentation potential. Internal values are bounded to 0.1–1.0; the web UI displays the rounded value on a 0–100 scale. The implementation and regression tests are maintained in `web/src/lib/domainScoring.ts`, `agents/multi_agent_engine.py`, `web/src/__tests__/algorithm.test.ts` and `tests/test_scoring_contract.py`. A change to this formula is a domain change and must update all relevant contract locations together.

## 4. Occupation Crosswalk

DISCO-08 and O*NET/other occupation taxonomies can provide useful task-level evidence, but a crosswalk from an occupation to a Danish education programme is not equivalent to an observed education-level labour-market outcome.

Any such mapping must state:

- mapping source
- mapping method
- whether the mapping is official or heuristic
- confidence

Where one programme plausibly leads to several occupations, a single occupation should not be presented as the complete career outcome without qualification.

### O*NET 31.0 model input

Model version 2026.6 uses O*NET 31.0 Work Activities importance ratings for programmes that already have a non-default DISCO code. Importance ratings are normalized from the O*NET 1–5 scale to 0–1. A documented deterministic model combines information-processing activities, cognitive activities and human/physical safeguards into `automation_risk` and `augmentation_potential`. Occupation scores are aggregated to the relevant ISCO/DISCO group median through the O*NET-ESCO crosswalk.

The activity groups, coefficients, clipping bounds and input hashes are defined in `etl/migrate_onet31.py` and `data/sources/onet31_source_manifest.json`. These are owner-selected model assumptions. O*NET does not publish an automation probability or approve this derived score.

Activation is deliberately partial: 569 of 1,413 programmes have a non-default legacy DISCO mapping and receive O*NET 31.0-derived model inputs. The remaining 844 do not have defensible O*NET 31.0 programme-level coverage. Even for migrated programmes, programme-to-DISCO remains a crosswalk whose confidence must remain visible.

### Sensitivity and rank stability

`etl/validate_model_stability.py` evaluates the mapped cohort under automation-resilience weights of 60%, 70%, 75%, 80% and 90%, with the remainder assigned to augmentation. It uses average ranks for ties and reports rank correlation, top-20 overlap and rank shifts against the canonical 75/25 formula.

The current deterministic report shows that 70/30 and 80/20 are very close to 75/25, while 60/40 and 90/10 cause materially larger movement outside the top group. Large shifts must be interpreted alongside the model's coarse occupation groups and many tied programme scores. The report deliberately excludes all 844 legacy/default programmes.

This analysis answers only whether the published ordering is sensitive to formula weights. It is not an empirical test of employment outcomes, causal AI effects or individual predictions. A representative human/domain review remains an external validation requirement.

### Legacy/default programmes

Legacy/default AI values may be retained in historical/generated artefacts for traceability, but they must not create programme-to-programme ranking differences as though they were programme-specific evidence. In the deployed client ranking, unsupported AI dimensions are neutralised to 50. This value is a **ranking placeholder**, not an estimate of the true AI score.

## 5. Recommendation Score and Ranking Evidence

The conceptual recommendation model contains components for:

- `interest_fit`
- `ai_resilience`
- `labour_demand`
- `salary_growth`
- `location_fit`

The product has two scoring contexts that must not be conflated:

### Client catalogue ranking

The deployed Next.js catalogue must not gain relative ranking differences from metrics whose programme-level evidence is not established.

Current policy:

- O*NET 31.0 AI input may differentiate a programme only when a non-baseline O*NET 31.0 mapping exists.
- Legacy/default AI input is neutralised to 50.
- Client-catalogue `labour_demand` and `salary_growth` are neutralised to 50 while their programme-level source/population/period/transformation are `PROVENANCE_REQUIRED`.
- A neutral 50 is not evidence and must be labelled as such. Its purpose is to prevent missing evidence from rewarding or penalising one programme relative to another while preserving the numeric UI contract.

This means some preference sliders may have little or no discriminating power until better provenance is available. That limitation must be visible rather than hidden by plausible defaults.

### Strict Python analytics ranking

`etl/build_education_profiles.py` only rebuilds `education_profile_scores` when the required education, labour, salary, DISCO and AI sources/mappings are complete. In that stricter dataset, labour and salary indicators may be used as derived signals because the source chain is explicit. The Python recommendation engine must still reject missing/non-finite core metrics rather than inventing fallback values.

Interest matching is currently a deterministic lexical/subject-alignment heuristic. It must not be described as a psychometric assessment or validated personality model.

Location matching distinguishes `STRUCTURED`, `TITLE_FALLBACK`, and `UNKNOWN`; title fallback has lower confidence than structured location data.

## 6. Evidence Engine

The evidence engine contains a registry of candidate sources with metadata weights. These weights express source-priority configuration only.

They do **not** constitute:

- programme-level evidence quality
- statistical consensus
- probability that a source supports a claim
- validation of every programme

Programme-level evidence must be attached to concrete claims. `programme_evidence_status = NOT_ESTABLISHED` is valid when such a relationship has not been established.

The public AI Insights page may present current research and official contextual statistics when every item records its source URL, publication date, geography, epistemic status, student-facing interpretation and material limitation. These items are **context only** and must not change programme rankings unless a separate, documented programme-level mapping and validation step establishes that use.

The generated registry is written to both `data/evidence_knowledge_base.json` and `web/src/data/evidence_knowledge_base.json`. The web copy is the deployable snapshot because root data files are intentionally excluded from Vercel builds.

## 7. Econometric Validation Status

The repository previously contained a TWFE/DiD routine whose dependent variable contained a platform-generated model metric. That construction could not independently validate the same metric and has been removed.

`etl/reproduce_econometric_results.py` now produces descriptive KOT diagnostics only and explicitly reports that no causal/econometric validation is performed.

Observed KOT admission data may be used for genuine descriptive analysis. Any future causal model must use an independently observed outcome and clearly document treatment, control, identification assumptions and pre-trend diagnostics.

---

## 8. Scenario Simulation

The scenario engine produces model-based simulations under explicit macro assumptions. Percentiles from Monte Carlo simulation are simulation uncertainty ranges, not empirical confidence intervals.

They must be described as **model uncertainty / simulation range**, not as statistical confidence intervals for an observed population parameter.

---

## 9. Data Quality Labels

The UI and API should distinguish:

- `OBSERVED`
- `DERIVED`
- `CROSSWALK`
- `MODEL`
- `PROVENANCE_REQUIRED`
- `UNKNOWN`

This prevents a model-generated score from being visually presented as an observed fact.

---

## 10. Limitations

- AI metrics are model-based and/or occupation-crosswalk estimates.
- O*NET is US occupational data and requires a documented crosswalk before Danish interpretation.
- KOT admission statistics describe admissions/applicant selection, not labour-market demand.
- Salary and employment metrics must not be presented as programme-specific facts unless their underlying population and mapping are documented.
- A neutral placeholder in ranking is not an estimate of the programme's true value.
- Recommendations are decision support, not deterministic predictions or professional career advice.
- The system must expose uncertainty and missing provenance rather than inventing precision.
- Newer upstream taxonomy versions do not become score inputs merely by being listed in the registry. O*NET 31.0 is active only for the documented 40.3% programme subset until additional defensible mappings exist.
